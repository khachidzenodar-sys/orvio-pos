# კერძების ფოტოები

ამ შესაძლებლობით მენეჯერს შეუძლია მენიუს თითოეულ პროდუქტს, კერძს ან სასმელს ფოტო დაუმატოს, შეუცვალოს ან წაუშალოს. ფოტო ჩანს შეკვეთის ეკრანის ბარათებზე, რომ მოლარემ კერძი სწრაფად იპოვოს. მენიუს მართვის სიაში ჩანს პატარა ესკიზი. ფოტოს გარეშე პროდუქტი ისე გამოიყურება, როგორც დღეს.

---

## ნაწილი 1. მფლობელისა და მენეჯერისთვის

### როგორ დავამატო ფოტო

1. გახსენით **მენიუ** და პროდუქტის გასწვრივ დააჭირეთ **რედაქტირებას**.
2. ფანჯრის **ფოტო** განყოფილებაში დააჭირეთ **„ფოტოს დამატება“**-ს.
   - კომპიუტერზე აირჩიეთ ფაილი. ფაილის ფოტოს ველზე გადმოთრევაც შეიძლება.
   - პლანშეტსა და ტელეფონზე შეგიძლიათ კამერით გადაიღოთ ან გალერეიდან აირჩიოთ.
3. პროგრამა ფოტოს თვითონ ამცირებს და კუმშავს. ეკრანზე ჩანს შედეგი და მისი ზომა, მაგალითად „24 კბ · 400×300“.
4. შეიყვანეთ **მენეჯერის კოდი** და დააჭირეთ **„შენახვა“**-ს. **„გაუქმება“** წინასწარ ნახვას გააუქმებს და არაფერს შეცვლის.

ახალ პროდუქტს ფოტოს ვერ დაუმატებთ, სანამ პროდუქტს ერთხელ არ შეინახავთ. შენახვის შემდეგ ხელახლა გახსენით რედაქტირება.

### როგორ შევცვალო ან წავშალო ფოტო

- ფოტოიან პროდუქტს აქვს ღილაკები **„ფოტოს შეცვლა“** და **„ფოტოს წაშლა“**.
- ორივე მოქმედება მენეჯერის კოდს ითხოვს. არასწორი კოდის შემთხვევაში არაფერი იცვლება.
- წაშლის შემდეგ ბარათი ძველ, მხოლოდ ტექსტიან სახეს უბრუნდება.
- პროდუქტის სახელის, ფასის ან განყოფილების შეცვლა ფოტოს არ შლის.

### რა ფაილები მიიღება

| ფაილი | შედეგი |
| --- | --- |
| JPEG, PNG, WebP | მიიღება |
| HEIC (iPhone) | მიიღება მხოლოდ მაშინ, თუ ბრაუზერს მისი გახსნა შეუძლია. თუ არა, გამოჩნდება თხოვნა, რომ ფოტო JPEG ან PNG ფორმატში შეინახოთ |
| 15 მბ-ზე დიდი ფაილი | არ მიიღება: „ფაილი ძალიან დიდია (მაქს. 15 მბ).“ |
| PDF, ტექსტი, სურათად გადარქმეული სხვა ფაილი | არ მიიღება: „აირჩიეთ სურათი (JPEG, PNG, WebP).“ |

### ლიმიტები

- თითო ფოტო ინახება მაქსიმუმ **400 პიქსელი** გრძელ მხარეზე და ჩვეულებრივ **≈20–40 კბ** იკავებს.
- ერთ მენიუში შეიძლება იყოს მაქსიმუმ **60 ფოტო**. ყველა ფოტოს ჯამური ზომა არ უნდა აღემატებოდეს **≈1.3 მბ**-ს (1 800 000 სიმბოლოს). ლიმიტის ამოწურვისას პროგრამა გეტყვით, რომ ჯერ რომელიმე ძველი ფოტო წაშალოთ.
- ბრაუზერის დემოს მეხსიერება შეზღუდულია (≈5 მბ). თუ ის გაივსება, გამოჩნდება შეტყობინება „ბრაუზერის მეხსიერება გავსებულია — ფოტო ვერ შეინახა. წაშალეთ ზოგიერთი ფოტო.“ უკვე შენახული მონაცემები არ იკარგება.

### სად ინახება და როგორ ვიცავ ფოტოებს

- **ბრაუზერის დემო:** ამავე ბრაუზერში, დანარჩენ მონაცემებთან ერთად.
- **Windows პროგრამა:** კომპიუტერის მონაცემების საქაღალდეში, დანარჩენ მონაცემებთან ერთად. პროგრამის დახურვისა და ხელახლა გახსნის შემდეგ ფოტოები რჩება.
- **ანგარიში (/workspace):** სერვერზე. ერთ კომპიუტერზე დამატებული ფოტო მეორეზე გვერდის განახლების შემდეგ გამოჩნდება.
- **სარეზერვო ასლი** ფოტოებსაც შეიცავს. აღდგენისას ისინი ზუსტად ბრუნდება. ფოტოების გამო ასლის ფაილი რამდენიმე მეგაბაიტით შეიძლება გაიზარდოს.
- ჩეკებზე და სამზარეულოს/ბარის ბილეთებზე ფოტო **არასდროს** იბეჭდება.

### შემოწმების მოკლე სცენარი

1. დაამატეთ ფოტო „ხაჭაპურს“ და შეინახეთ კოდით 1234 (დემო).
2. გახსენით მაგიდა და დარწმუნდით, რომ ბარათზე ფოტო ჩანს, სახელი და ფასი კი სრულად იკითხება.
3. შეცვალეთ ხაჭაპურის ფასი. ფოტო უნდა დარჩეს.
4. შექმენით სარეზერვო ასლი, წაშალეთ ფოტო და აღადგინეთ ასლი. ფოტო უნდა დაბრუნდეს.
5. სცადეთ PDF ფაილის არჩევა. უნდა გამოჩნდეს ქართული შეტყობინება და არაფერი უნდა შეიცვალოს.

## ნაწილი 2. ტექნიკური დიზაინი

### 2.1 არჩეული მიდგომა და მისი შედეგები

**ფოტო ინახება პირდაპირ პროდუქტზე, როგორც შეკუმშული data URL:** `Product.photo?: string`.

რატომ ეს და არა ცალკე images map ან ცალკე storage key:

| | data URL პროდუქტზე (არჩეული) | ცალკე images map / key |
| --- | --- | --- |
| შენახვის პორტი (`KeyValueStore`) | უცვლელი | ახალი key და მეორე ჩაწერა, რაც ორ key-ს შორის ატომურობის პრობლემას ქმნის |
| Supabase | უცვლელი (ერთი JSON დოკუმენტი, იგივე CAS ვერსია) | ახალი სვეტი ან ცხრილი, ახალი API |
| სარეზერვო ასლი | ავტომატურად შედის დოკუმენტში | ცალკე უნდა შეიფუთოს და აღდგეს |
| ვერსიები და კონფლიქტები | იგივე `version` შემოწმება | მეორე ვერსიის სისტემა |
| ნაკლი | დოკუმენტი იზრდება (≤ ~1.8 მლნ სიმბოლო), ყოველ წაკითხვასა და ჩაწერაში მთელი დოკუმენტი გადადის | — |

ნაკლი ორი ლიმიტით კონტროლდება: შეკუმშვით (~40 კბ ფოტოზე) და დოკუმენტის ზედა ზღვრით (60 ფოტო, 1 800 000 სიმბოლო). ანგარიშის რეჟიმში 8-წამიანი ფონური განახლება აღარ ჩამოტვირთავს მთელ დოკუმენტს, თუ ვერსია არ შეცვლილა (§2.7). ასე ფოტოები ქსელს არ ტვირთავს.

ხაზების snapshot-ები (`Line`, `Ticket.lines`) ფოტოს **არ** აკოპირებენ. `addItem` მხოლოდ სახელს, ფასს და განყოფილებებს იღებს. ამიტომ ჩეკები, ბილეთები, ESC/POS და ბრაუზერის ბეჭდვა ბაიტ-ბაიტ უცვლელია. `lib/printing/*` არ იცვლება.

CSP (`src-tauri/tauri.conf.json`) უკვე უშვებს `img-src 'self' data:`. ის **არ** იცვლება. გარე URL-ები validation-ის დონეზეა აკრძალული, ამიტომ CSP-ის გაფართოება საჭირო არ არის.

### 2.2 ლიმიტები (ერთადერთი წყარო: `lib/product-photo.ts`)

| კონსტანტა | მნიშვნელობა | აზრი |
| --- | --- | --- |
| `PHOTO_MAX_SIDE` | 400 | გრძელი მხარე პიქსელებში, გადიდება არასდროს |
| `PHOTO_TARGET_CHARS` | 54 000 | ≈40 კბ ბინარული. Encoder ცდილობს ამაში ჩაეტიოს |
| `PHOTO_MAX_CHARS` | 60 000 | მკაცრი ზღვარი თითო data URL-ზე (≈45 კბ) |
| `PHOTO_MAX_COUNT` | 60 | ფოტოიანი პროდუქტების მაქსიმუმი |
| `PHOTO_MAX_TOTAL_CHARS` | 1 800 000 | ყველა ფოტოს ჯამი დოკუმენტში |
| `PHOTO_SOURCE_MAX_BYTES` | 15 × 1024 × 1024 | საწყისი ფაილი, მოწმდება დეკოდირებამდე |
| `PHOTO_ACCEPT` | `image/jpeg,image/png,image/webp,image/heic,image/heif` | `<input accept>` |

localStorage-ის ბიუჯეტი (≈5 მლნ სიმბოლო origin-ზე): 30 ფოტო × ≤54 000 ≈ 1.6 მლნ, დემოს დანარჩენი მონაცემები კი < 0.2 მლნ, ანუ < 2 მლნ. ეს ტესტით მოწმდება (§2.9). `restoreBackup` აღდგენამდე ინახავს `orvio.before-restore.*` ასლს. ბრაუზერის დემო ინახავს მხოლოდ ბოლო ასლს (ძირითადი დოკუმენტი + 1 ასლი ≈ 2 × 2 მლნ ჩაეტევა). ასლების სია ინახება `orvio.restore-copies` გასაღებში. თუ მეხსიერება გავსებულია, ახალი ასლი ძველ ასლს ატომურად გადაეწერება. თუ იგივე მონაცემები აღდგება ხელმეორედ, ახალი ასლი საჭირო არ არის. თუ ადგილი მაინც არ არის, აღდგენა წყდება და მიმდინარე დოკუმენტი უცვლელი რჩება. Desktop ინახავს ყველა ასლს. Quota-ს შეცდომისას აღდგენა უსაფრთხოდ წყდება და მიმდინარე დოკუმენტი უცვლელი რჩება. ჯამური ლიმიტი მხოლოდ `setProductPhoto` მოქმედებაში მოწმდება. Strict validation მხოლოდ თითო ფოტოს ფორმატსა და ზომას ამოწმებს, რომ ლიმიტის მომავალმა ცვლილებამ ძველი დოკუმენტები არ დააზიანოს.

### 2.3 სუფთა მოდული `lib/product-photo.ts` (დეველოპერი A)

იმპორტების გარეშე (Node strip-types runner-ში პირდაპირ მუშაობს).

```ts
export const PHOTO_MAX_SIDE = 400;
export const PHOTO_TARGET_CHARS = 54_000;
export const PHOTO_MAX_CHARS = 60_000;
export const PHOTO_MAX_COUNT = 60;
export const PHOTO_MAX_TOTAL_CHARS = 1_800_000;
export const PHOTO_SOURCE_MAX_BYTES = 15 * 1024 * 1024;
export const PHOTO_ACCEPT = 'image/jpeg,image/png,image/webp,image/heic,image/heif';

// Georgian user-facing messages, shared by domain, store and UI.
export const PHOTO_MESSAGES: {
  notImage: string;      // 'აირჩიეთ სურათი (JPEG, PNG, WebP).'
  tooLarge: string;      // 'ფაილი ძალიან დიდია (მაქს. 15 მბ).'
  heic: string;          // 'ამ ბრაუზერს HEIC ფოტოს გახსნა არ შეუძლია. შეინახეთ ფოტო JPEG ან PNG ფორმატში და სცადეთ ხელახლა.'
  tooHeavy: string;      // 'ფოტო შეკუმშვის შემდეგაც ძალიან დიდია. სცადეთ სხვა ფოტო.'
  invalid: string;       // 'ფოტო არასწორია. დასაშვებია მხოლოდ JPEG, PNG ან WebP სურათი.'
  countLimit: string;    // 'ფოტოების ლიმიტი ამოიწურა (მაქს. 60). ახლის დასამატებლად წაშალეთ რომელიმე ფოტო.'
  totalLimit: string;    // 'ფოტოების ჯამური ზომის ლიმიტი ამოიწურა. წაშალეთ რომელიმე ფოტო ან გამოიყენეთ უფრო მარტივი სურათი.'
  quota: string;         // 'ბრაუზერის მეხსიერება გავსებულია — ფოტო ვერ შეინახა. წაშალეთ ზოგიერთი ფოტო.'
};

// Exactly ^data:image/(jpeg|png|webp);base64,[A-Za-z0-9+/]+=*$, length <= PHOTO_MAX_CHARS,
// base64 payload length % 4 === 0. Length is checked BEFORE the regex.
export function isValidProductPhoto(value: unknown): value is string;

// Decoded binary size of a data URL (base64 math, no decoding).
export function photoBytes(dataUrl: string): number;
// Rounded-up kilobytes for UI ("24 კბ").
export function photoKilobytes(dataUrl: string): number;

export type PhotoUsage = {count: number; chars: number};
// Counts photos of all products, optionally ignoring one product (the one being replaced).
export function photoUsage(products: readonly {id: string; photo?: string}[], exceptId?: string): PhotoUsage;
// null when `photo` may be stored on `productId`; otherwise PHOTO_MESSAGES.countLimit / totalLimit.
export function photoLimitError(products: readonly {id: string; photo?: string}[], productId: string, photo: string): string | null;

// Pre-decode checks of a picked file. null = OK to decode.
// Order: size > PHOTO_SOURCE_MAX_BYTES → tooLarge; type/extension not jpeg/png/webp/heic/heif → notImage.
// Empty `type` is accepted when the extension is .jpg/.jpeg/.png/.webp/.heic/.heif (Windows often gives '' for HEIC).
export function sourceFileError(file: {name: string; type: string; size: number}): string | null;
export function isHeicFile(file: {name: string; type: string}): boolean;

// Scale to fit within maxSide, never enlarge, keep aspect ratio, integer px >= 1.
export function fitWithin(width: number, height: number, maxSide?: number): {width: number; height: number};

// Encoder ladder used by the browser adapter: tried in order until a result <= PHOTO_TARGET_CHARS;
// the smallest valid result <= PHOTO_MAX_CHARS is the fallback; otherwise tooHeavy.
export const PHOTO_ENCODE_STEPS: readonly {maxSide: number; quality: number}[];
```

**ბრაუზერის adapter `lib/adapters/image-compressor.ts`** (მხოლოდ ბრაუზერში. იმპორტს მხოლოდ client კომპონენტი აკეთებს):

```ts
export type CompressedPhoto = {dataUrl: string; width: number; height: number; kilobytes: number};
// Throws Error(PHOTO_MESSAGES.*) with a Georgian message; never returns an invalid photo.
export async function compressProductPhoto(file: File): Promise<CompressedPhoto>;
```
ალგორითმი:
1. `sourceFileError(file)` → throw.
2. დეკოდირება: `createImageBitmap(file, {imageOrientation: 'from-image'})` (EXIF ორიენტაცია). Fallback: `new Image()` + `URL.createObjectURL` + `img.decode()` (თანამედროვე ბრაუზერები `<img>`-ზე EXIF-ს ავტომატურად იყენებენ), შემდეგ კი `URL.revokeObjectURL`. დეკოდირების შეცდომისას: `isHeicFile(file)` → `heic`, სხვა შემთხვევაში `notImage`. გადარქმეული PDF აქ ვარდება.
3. `PHOTO_ENCODE_STEPS`-ის თითოეული ნაბიჯისთვის: `fitWithin(w, h, step.maxSide)` → `<canvas>` → `ctx.fillStyle='#fff'; fillRect` (PNG-ის გამჭვირვალობა) → `drawImage` → `canvas.toDataURL('image/webp', q)`. თუ შედეგი `data:image/webp`-ით არ იწყება (ძველი Safari), გამოიყენება `'image/jpeg'`. პირველი შედეგი, რომელიც აკმაყოფილებს `isValidProductPhoto`-ს და ≤ `PHOTO_TARGET_CHARS`-ია, ბრუნდება. სხვა შემთხვევაში ბრუნდება ყველაზე პატარა ვალიდური შედეგი. თუ ვალიდური შედეგი არ არის, ვარდება `tooHeavy`.
4. `bitmap.close()` finally-ში. ერთი canvas გამოიყენება ხელახლა.
